# Проекты STM32 C/C++

Режим разработки как в Keil или STM32CubeIDE: настоящий ARM-проект без обвязки Arduino (C/C++, CMSIS, startup, скрипт компоновщика, конфигурации Debug и Release), прошивка и отладка через ST-Link. Режим Arduino остаётся как есть. Этот документ описывает фундамент (этап A); сборка, прошивка, база чипов и редактор подключаются отдельными этапами через интерфейсы ниже.

## Этапы

| Этап | Что делает | Где подключается |
|------|-----------|------------------|
| A | модель проекта, режим в интерфейсе, мастер, заглушки | `src/main/pro/`, `src/renderer/src/pro/` |
| B | сборка arm-none-eabi-gcc | `proRegistry.register('build', …)` |
| C | прошивка, GDB-сервер, отладка (ST-Link, J-Link, CMSIS-DAP; OpenOCD), вывод SWO | `register('programmer', …)`, `register('debug', …)` |
| D | база чипов (выводы, память, файлы CMSIS) | `register('chips', …)`; мастер и панель «Чипы и платы» берут данные оттуда |
| E | редактор и CubeMX-подобный конфигуратор выводов и тактирования | `src/shared/pro/pinconfig/`, вкладка «Пины и тактирование», файл `avride.pins.json` (раздел ниже) |

## Рабочая область STM32

- Кнопка «Создать проект» открывает выбор формата. «STM32 C/C++» ведёт к выбору чипа и шаблона. Для Pico доступны «Скетч Arduino» и «CircuitPython для Pico». CircuitPython открывает редактор одного `.py` с записью `code.py` на диск `CIRCUITPY`.
- При открытии папки IDE выбирает рабочую область по формату проекта. Папка с `avride.project.json` открывается как STM32, включая случай ошибки в манифесте. Остальные папки открываются как Arduino.
- Шапка Pro: «Собрать», «Прошить», «Отладка», «Конфигурация: Debug», «Цель: STM32F103C8», «Программатор: ST-Link». Кнопки неактивны, пока соответствующий провайдер не реализован (`ProviderInfo.implemented`), и объясняют это подсказкой; сами включатся, когда этап зарегистрирует провайдер.
- В боковой панели доступны файлы, поиск, структура проекта, каталог чипов, веб-дизайнер и настройки. Монитор порта, размер программы, отладка и SWO открываются как вкладки через «Инструменты». Команда «Прошить» открывает мастер и ждёт подтверждения записи.
- Ctrl+B и Ctrl+U в проекте STM32 вызывают `runProAction('build' | 'flash')`.

## Файл проекта `avride.project.json` (схема 1)

```json
{
  "schemaVersion": 1,
  "name": "BluePillBlink",
  "target": {
    "vendor": "st",
    "family": "STM32F1",
    "chip": "STM32F103C8T6",
    "board": "Blue Pill",
    "core": "cortex-m3",
    "clock": { "hseHz": 8000000, "sysclkHz": 72000000 },
    "memory": {
      "flash": { "origin": "0x08000000", "size": 65536 },
      "ram": { "origin": "0x20000000", "size": 20480 }
    }
  },
  "sources": ["src"],
  "includes": ["include"],
  "defines": ["STM32F103xB"],
  "linkerScript": "linker/STM32F103C8T6_FLASH.ld",
  "startupFile": "startup/startup_stm32f103xb.s",
  "configurations": {
    "Debug": { "optimization": "Og", "debugLevel": "g3", "defines": ["DEBUG"], "extraFlags": [] },
    "Release": { "optimization": "Os", "debugLevel": "none", "defines": ["NDEBUG"], "extraFlags": [] }
  },
  "toolchain": { "kind": "arm-none-eabi-gcc" },
  "programmer": { "kind": "stlink", "interface": "swd", "openocdTarget": "target/stm32f1x.cfg" }
}
```

Правила:

- Пути относительные, с разделителем `/`, без `..` и диска. `sources` и `includes` — файлы или папки (папки обходятся рекурсивно).
- Адреса памяти — hex-строки `0x…`, размеры — байты. `target.memory.extra` — необязательные области (`name`, `origin`, `size`: CCM, SRAM2).
- Необязательные поля: `target.board`, `target.fpu` (`fpv4-sp-d16`, `fpv5-d16`, `fpv5-sp-d16`), `target.floatAbi` (`soft`, `softfp`, `hard`), `target.clock`, `svd`, `toolchain.version`, `programmer.openocdTarget`.
- `core`: `cortex-m0`, `cortex-m0plus`, `cortex-m3`, `cortex-m4`, `cortex-m7`, `cortex-m33`. `optimization`: `O0 O1 O2 O3 Os Og Oz`. `debugLevel`: `none g1 g2 g3`. `programmer.kind`: `stlink`, `jlink`, `cmsis-dap`.
- Конфигурации Debug и Release обязательны, можно добавлять свои. Активная конфигурация в файл не пишется (это состояние интерфейса, `proStore.config`).
- Папка результатов сборки по соглашению `build/<Конфигурация>`.
- Неизвестные поля дают предупреждение и игнорируются; ошибки содержат путь к полю (`target.memory.flash.origin: …`).

## Интерфейсы провайдеров (`src/main/pro/interfaces.ts`)

Все методы асинхронные. У каждого провайдера есть `id` и `implemented`. Операции получают `ProjectContext { root, project, configuration }` и необязательные `RunOptions { onLog, signal }`.

- `BuildProvider` (B): `configure(ctx) → BuildPlan`, `build(ctx, opts?) → BuildResult`, `clean(ctx)`, `size(ctx) → SizeReport`, `map(ctx) → MapReport`.
- `ProgrammerProvider` (C): `listProbes() → Probe[]`, `flash(ctx, probe, {file, address?, verify?, reset?})`, `erase(ctx, probe, {mass?})`, `startGdbServer(ctx, probe) → {port, stop()}`.
- `DebugProvider` (C): `launch(ctx, probe) → DebugSession` (resume, pause, step*, breakpoints, stack, registers, memory, события).
- `ChipDatabase` (D): `getChip(id)`, `listChips(query?)`, `pinFunctions(chipId)`, `memoryMap(chipId)`.

Заглушки (`stubs.ts`) бросают `NotImplementedError` с русским текстом («Сборка ARM-проектов ещё не реализована…»), `isNotImplemented(e)` отличает их от настоящих ошибок.

### Регистрация

```ts
import { proRegistry } from './pro/registry'
proRegistry.register('build', myBuildProvider) // вызывать при старте main (рядом с registerProIpc)
```

`proRegistry.status()` отдаёт сводку `{build, programmer, debug, chips}: {id, implemented}`; интерфейс получает её через `window.api.pro.providers()` (читается при показе шапки).

### IPC (`src/main/pro/ipc.ts`, `window.api.pro`)

| Метод | Назначение |
|-------|-----------|
| `providers()` | сводка провайдеров |
| `readProject()` | `avride.project.json` открытой папки: `{found:false}`, `{found, ok:true, project}` или `{found, ok:false, error}` |
| `create(name, parent, chip, template)` | создаёт папку со структурой, открывает её в main; renderer затем вызывает `project.open` |
| `action(kind, configuration)` | `build`, `clean`, `flash`, `debug` через реестр; нереализованное возвращает понятную ошибку |

## Прошивка и отладка (этап C)

Код: `src/main/pro/openocd/` (командные строки, разбор журналов, список программаторов, запуск OpenOCD, приём SWO), `src/shared/pro/programmers.ts` (общий слой «тип программатора»), `src/shared/pro/itm.ts` (разбор потока ITM), `src/main/pro/debug/` (разбор GDB/MI, сессия, разбор SVD), `src/main/pro/tools/` (поиск программ `findTool` / `locateTool`, установка xPack OpenOCD), `src/main/pro/hardware.ts` (IPC `pro:*`), интерфейс `src/renderer/src/pro/{HwPanel,DebugPanel,hwStore}`.

- Поиск программ: переменная `AVRIDE_PRO_<OPENOCD|GDB|GCC>` → путь из настройки (`userData/pro-tools.json`) → `userData/pro-tools/**/bin` → STM32CubeIDE и xPack → PATH. Установка OpenOCD «одной кнопкой» скачивает xPack OpenOCD (релиз `v0.12.0-7`, Windows x64) только после подтверждения и сверяет SHA-256.
- Прошивка: `openocd -f interface/<программатор>.cfg -c "transport select <транспорт>" [-c "adapter serial …"] -f target/<цель>.cfg -c "adapter speed 1800" -c "program {файл} [адрес] verify reset exit"`; программатор и транспорт — по таблице ниже. Цель — `programmer.openocdTarget` проекта, иначе из базы чипов. Файл — `build/<Конфигурация>/<имя проекта>.elf` (или единственный .elf в папке).
- Отладка: OpenOCD как GDB-сервер + `arm-none-eabi-gdb --interpreter=mi3`, символы `-file-symbol-file`, подключение `-target-select extended-remote`. Запись во Flash — только кнопка «Загрузить программу в устройство…» с подтверждением; запись в регистры и память — только с подтверждением.
- Горячие клавиши: F5 начать/продолжить, F10 шаг, F11 внутрь, Shift+F11 наружу, Shift+F5 стоп, F9 точка останова.
- Тесты: юнит (`openocd/*.test.ts`, `debug/*.test.ts`, `tools/tools.test.ts`), e2e `y-pro-flash` и `z-pro-install` на имитаторах (`scripts/e2e/fakes`). Инструкция для проверки на плате: [pro-hardware-test.md](pro-hardware-test.md).
- Не сделано: установка arm-none-eabi-gdb (её ставит этап «Сборка»), SEGGER RTT и полухостинг (см. ниже «Что не поддержано»).

### Типы программаторов (ST-Link, J-Link, CMSIS-DAP)

Тип записан в `programmer.kind` файла проекта (`stlink`, `jlink`, `cmsis-dap`), выбирается в панели «Прошивка» (поле «Тип»; запись в `avride.project.json`, устройство не затрагивается). Старый файл без `kind` или `interface` читается как ST-Link/SWD (предупреждение при проверке). Неизвестное значение — ошибка с путём `programmer.kind`.

| Тип | Файл интерфейса OpenOCD | Транспорт | Серийный номер | USB (перечисление, без обращения к устройству) |
|---|---|---|---|---|
| ST-Link | `interface/stlink.cfg` | `transport select hla_swd` | `adapter serial` | VID 0483: PID 3748 (V2), 374B и 3752 (V2-1), 374E, 374F, 3753, 3754 (V3) |
| J-Link | `interface/jlink.cfg` | `transport select swd` | `adapter serial` (серийный номер J-Link) | VID 1366 (SEGGER), PID из правил udev OpenOCD: 0101-0105, 0107, 0108, 1010-1018, 1020, 1051, 1055, 1061 |
| CMSIS-DAP | `interface/cmsis-dap.cfg` | `transport select swd` | `adapter serial` | Arm DAPLink 0D28:0204, Raspberry Pi Debug Probe 2E8A:000C; остальные — по слову «CMSIS-DAP» в названии (так их ищет и сам OpenOCD, `cmsis_dap_usb_bulk.c`) |

- `cmsis_dap_vid_pid` не нужен: OpenOCD 0.12 без VID/PID сам выбирает устройства со строкой «CMSIS-DAP» в названии продукта или интерфейса; несколько устройств различаются `adapter serial`. Если у программатора другое название, VID/PID задаёт пользователь в своих настройках OpenOCD (IDE этого пока не делает).
- Источники: OpenOCD User's Guide (openocd.org/doc, «Debug Adapter Configuration»), исходники OpenOCD v0.12.0 (`tcl/interface/*.cfg`, `contrib/60-openocd.rules`, `src/jtag/drivers/{jlink,cmsis_dap,cmsis_dap_usb_bulk}.c`), руководство SEGGER (VID 1366, PID 0101 у первого J-Link), документация Raspberry Pi (Debug Probe, CMSIS-DAP).
- Выбор программатора: без явного выбора берётся первый устройство того типа, что записан в проекте; программатор другого типа сам не подставляется (панель показывает «найдено другое: J-Link — Использовать»). Цель OpenOCD берётся из `programmer.openocdTarget`, иначе из базы чипов (D). Перед запуском проверяется, что в папке `scripts` рядом с OpenOCD (xPack: `openocd/scripts`) есть файл интерфейса и файл цели; иначе понятная ошибка с именами недостающих файлов.
- Драйверы Windows: IDE **ничего не устанавливает**, только объясняет. ST-Link: STSW-LINK009 или WinUSB через Zadig. J-Link: OpenOCD работает с J-Link через libusb, нужен WinUSB (Zadig); драйвер SEGGER для этого не подходит (после замены программы SEGGER этот J-Link не видят, пока драйвер не вернут). CMSIS-DAP v2 использует WinUSB, который устройство выдаёт само, v1 — HID без драйвера.
- Ошибки по типам (строки OpenOCD 0.12.0 проверены по исходникам): J-Link — «No J-Link device found» (нет устройства; если оно видно в системе без WinUSB — объясняется как «не тот драйвер»), «Failed to open device» (драйвер), «Multiple devices found, specify the desired device» (выберите по серийному номеру), «Device supports JTAG transport only» (нет SWD); CMSIS-DAP — «unable to find a matching CMSIS-DAP device», «CMSIS-DAP: SWD not supported».

### SWO / ITM (printf через ITM_SendChar)

Вкладка «SWO» («Инструменты» в проекте STM32). «Запустить» запускает отдельный OpenOCD, который подключается к **работающей** плате (не сбрасывает, не останавливает ядро, ничего не пишет во Flash) и отдаёт поток трассировки на TCP-порт localhost; IDE подключается клиентом, разбирает пакеты ITM и показывает текст порта 0. Командная строка (команды из OpenOCD User's Guide 0.12, «Architecture and Core Commands»):

```
openocd -f interface/<программатор>.cfg -c "transport select …" -f target/<цель>.cfg -c "adapter speed 1800"
  -c "gdb_port disabled" -c "telnet_port disabled" -c "tcl_port disabled"
  -c "foreach t [tpiu names] { $t configure -protocol uart -output :<порт> -traceclk <Гц ядра> -pin-freq <Гц SWO>; $t enable }"
  -c init -c "itm port 0 on"
```

- Объект TPIU создаёт скрипт цели (`tpiu create <чип>.tpiu`, например `stm32f1x.tpiu`), поэтому имя берётся из `tpiu names`; если блока нет, запуск останавливается с сообщением. Старая форма `tpiu config internal …` в 0.12 объявлена устаревшей и не используется; для ST-Link (hla) 0.12 принимает те же команды (исходник `arm_tpiu_swo.c`: ветка `transport_is_hla`).
- Поля «Частота ядра» (из проекта: `target.clock.sysclkHz`, иначе вводится вручную) и «Скорость SWO» (по умолчанию 2 МГц). Ядро в примере проекта не тактируется от PLL: введите реальную частоту.
- Разбор потока — `src/shared/pro/itm.ts` (чистые функции, юнит-тесты на фикстурах): пакеты SWIT (1, 2, 4 байта, порт — биты 7:3), переполнение 0x70, метки времени (локальные и глобальные), синхронизация (нули и 0x80), аппаратные источники DWT (пропускаются и считаются), UTF-8, разорванный границами кусков. Текст порта 0 — в консоли; байты других портов считаются в строке состояния; переполнения показываются предупреждением.
- Интерфейс: «Запустить/Остановить», «Очистить», «Сохранить…» (в файл), автопрокрутка, поля частот, справка «Как подключить SWO». SWO и прошивка/отладка взаимно исключают друг друга (программатор открывает один OpenOCD); кнопки и IPC объясняют это сообщением.
- Шаблон проекта «printf через SWO» (мастер; только Cortex-M3 и новее) и сниппеты редактора `swo` и `itm`: `swo_init()` включает TRCENA, разблокирует ITM, включает ITM и порт 0; `_write()` отправляет символы через CMSIS `ITM_SendChar`. Код (`src/shared/pro/swoCode.ts`) компилировался настоящим arm-none-eabi-gcc 14.2.1 (F103: сборка и компоновка, F411 и G474: компиляция) без замечаний при -Wall -Wextra.
- На ST-Link V2 для SWO нужен отдельный провод от вывода SWO микроконтроллера (обычно PB3) к выводу SWO программатора; у дешёвых «свистков» для Blue Pill его часто нет, а у клонов SWO может не работать. На Nucleo и Discovery SWO обычно уже соединён со встроенным ST-Link (смотрите схему платы).

### Что не поддержано и почему

- **SEGGER RTT** (`rtt setup <адрес> <размер> [ID]`, `rtt start`, `rtt server start <порт> <канал>`): команды есть в документации OpenOCD, но для работы нужен управляющий блок RTT в прошивке (исходники SEGGER RTT под лицензией SEGGER) и адрес блока из ELF; в этой версии не реализовано, чтобы не распространять чужой код и не имитировать то, что нельзя проверить без платы. Альтернатива — SWO.
- **Полухостинг** (`arm semihosting enable`): команда отсутствует в проверенных разделах документации OpenOCD, которые читались при разработке, не реализовано.
- SWO через J-Link и CMSIS-DAP: командная строка одинакова, но поддержка трассировки зависит от драйвера и версии OpenOCD; вживую не проверялась. SWO одновременно с отладкой не поддерживается.
- Установка драйверов (Zadig, SEGGER, ST) — только рекомендации в тексте.

## Сборка (этап B)

Кнопка «Собрать» (Ctrl+B) собирает выбранную конфигурацию встроенным сборщиком на Node: без make, ninja и CMake. Компилятор — `arm-none-eabi-gcc`.

### Как это работает

1. **Проверка** (`BuildProvider.preflight`). По порядку: есть ли скрипт компоновки, найден ли компилятор, есть ли настоящий startup и заголовки CMSIS (а не заготовка мастера), есть ли исходники. Чего не хватает — для того интерфейс показывает карточку с одним главным действием: «Создать по карте памяти», «Скачать и установить» компилятор, «Скачать и собрать» файлы CMSIS. После действия сборка продолжается сама.
2. **План** (`build/plan.ts`, `build/flags.ts`). Исходники — файлы и папки из `sources` (рекурсивно: `.c`, `.cpp`/`.cc`/`.cxx`, `.s`/`.S`) плюс `startupFile`. Ключи: `-mcpu`, `-mthumb`, `-mfpu`/`-mfloat-abi` по ядру и FPU проекта; `-O…` и `-g…` по конфигурации; `-ffunction-sections -fdata-sections -Wall`; `-D` из проекта, конфигурации и макрос устройства из базы чипов; `-I` из `includes`; для C `-std=gnu11`, для C++ `-std=gnu++17 -fno-exceptions -fno-rtti -fno-threadsafe-statics`, для ассемблера `-x assembler-with-cpp`. Компоновка: `-T <скрипт> -Wl,-Map,--cref -Wl,--gc-sections -Wl,--print-memory-usage --specs=nano.specs --specs=nosys.specs -static`, объекты через файл ответов, `-Wl,--start-group -lc -lm -Wl,--end-group`; при наличии C++ компонует `arm-none-eabi-g++`. Свои ключи конфигурации (`extraFlags`): `-Wl,…`, `-l…`, `-L…`, `-T…`, `--specs=…` уходят компоновщику, остальные — компилятору (`-m…`, `-flto` — обоим). Пути в командах абсолютные с «/»: gcc печатает их в сообщениях, и клик по строке в «Проблемах» открывает файл.
3. **Инкрементальность** (`build/incremental.ts`). Файл перекомпилируется, если нет объекта, изменился хэш команды (любой ключ), исходник или любой заголовок из `.d` (формат make, `-MMD -MP`) новее объекта. Компоновка — если что-то пересобрано, нет ELF, изменился скрипт или хэш команды линковки. Состояние — `build/<Конфигурация>/.avride-state.json`.
4. **Параллельность.** Число потоков — по числу ядер процессора; после первой ошибки новые файлы не запускаются, уже идущие дорабатывают и все их сообщения попадают в «Проблемы».
5. **Результат.** `build/<Конфигурация>/<имя>.elf`, `.bin`, `.hex` (`arm-none-eabi-objcopy`), `.map`; `arm-none-eabi-size` (text/data/bss); использование областей — из таблицы, которую печатает ld (`--print-memory-usage`), разбор `.map` дополняет её секциями и крупнейшими символами (`build/mapParse.ts`). В строке состояния Pro: «Собрано · Flash 12,4 КБ (19%) · RAM 2,1 КБ (10%)»; Flash = text + data, RAM = data + bss (в таблице областей RAM — как у ld, с резервом под кучу и стек). Переполнение области: ошибка «Область памяти FLASH переполнена на N байт».
6. **Вкладка «Размер программы»** (меню «Инструменты»): полоски Flash/RAM/CCMRAM… с процентами (цвет и подпись: «почти заполнено», «переполнение»), таблица секций, таблица самых больших символов с файлами.

### Компилятор

Порядок поиска (`build/toolchain.ts`, `toolchainStore.ts`): переменная `AVRIDE_PRO_GCC` (файл gcc или папка bin) → путь из настроек (Настройки → Режим работы → «Компилятор ARM», общий файл `userData/pro-tools.json` с этапом C) → установленный приложением (`userData/pro-tools/*/bin`) → PATH → Arm GNU Toolchain в Program Files → STM32CubeIDE (`C:\ST\…\gnu-tools-for-stm32…\tools\bin`) → xPack (`%APPDATA%\xPacks`). Каждый кандидат проверяется запуском `--version`.

Установка «одной кнопкой» (только Windows x64): xPack GNU Arm Embedded GCC 14.2.1-1.1 с GitHub (308 МБ, ≈ 1,7 ГБ на диске). Карточка перед скачиванием показывает размер, источник, проверку SHA-256 и лицензию; ход виден в строке прогресса и в «Выводе»; отмена убивает скачивание и распаковку. Сумма записана в коде и сверяется после скачивания (несовпадение — архив удаляется, установка прекращается). Распаковка штатным `tar.exe` Windows. Лицензии и ссылки на исходники — в `licenses/THIRD_PARTY.md`. В той же папке `pro-tools` этап C находит `arm-none-eabi-gdb`.

### Файлы поддержки чипа

Мастер создаёт проект, который собирается после одного подтверждения:

- `linker/<чип>_FLASH.ld` — **генерируется** (`build/linkerGen.ts`) по карте памяти проекта: области FLASH и RAM, дополнительные (CCMRAM и др.) со своими секциями `.ccmram`; соседние области базы (SRAM1+SRAM2, банки Flash) сливаются, основная RAM — самая большая (у H743 — AXI SRAM). Кнопка «Создать по карте памяти» (`pro:generate-linker`) воссоздаёт утерянный скрипт.
- `startup/startup_*.s`, `drivers/CMSIS/Include/*` (ядро), `drivers/CMSIS/Device/ST/STM32F1xx/{Include,Source}/*` — **скачиваются** из репозиториев ST (`cmsis-device-*`, `cmsis_core`, Apache-2.0) по тегам. Манифест `src/main/pro/support/manifest.ts` (генерируется `scripts/build-cmsis-manifest.mjs`) хранит для каждого файла путь, размер и git-SHA-1; адрес — неизменяемый коммит тега. Скачивание — только после подтверждения (источник, размер, лицензия), каждый файл сверяется, кэш лежит в `userData/pro/support`. Если в кэше уже всё есть, мастер копирует файлы в проект сразу, без сети.
- Для чипа, которого нет в базе, пакета поддержки нет: добавьте startup и заголовки вручную.

### Экспорт сборки

«Экспорт сборки…» (панель «Проект», вкладка «Размер», палитра команд) пишет в корень проекта `Makefile` (GNU make: `make`, `make CONFIG=Release`, `make clean`) и `CMakeLists.txt` (CMake 3.20+, Ninja или make). Ключи те же, что у встроенного сборщика. Файлы начинаются со строки «# Создан AVR IDE»; чужие файлы с такими именами заменяются только после подтверждения.

### Конфигурации

Панель «Проект» → «Конфигурации» → «Изменить…» (или палитра команд): оптимизация (`-O0 … -Oz`), отладочная информация (`-g1 … -g3`), макросы `-D`, дополнительные ключи; можно добавить свою конфигурацию (копия выбранной) и удалить свою. Запись — в `avride.project.json` (`pro:save-project`, с проверкой схемы).

## Конфигуратор выводов и тактирования (этап E)

Вкладка «Пины и тактирование» (кнопка в панели «Проект», команда палитры «Пины и тактирование…», код — `src/renderer/src/pro/pins/`) — облегчённый аналог STM32CubeMX. Работает с чипом проекта из `avride.project.json` и базой чипов (этап D): корпус рисуется по таблице выводов (LQFP/UFQFPN — четыре стороны, TSSOP — две, WLCSP — сетка шариков), цвет вывода показывает роль (GPIO, функция периферии, аналог, питание, особые, защищённые, конфликт). Слева дерево периферии (включить USART1, выбрать выводы сигналов), справа инспектор вывода или периферии, внизу вкладки «Тактирование» (блок-схема HSI/HSE → PLL → SYSCLK → AHB → APB1/APB2 → таймеры с частотами и проверкой пределов) и «Таблица пинов».

### Файл `avride.pins.json` (схема 1)

Лежит рядом с `avride.project.json`. Читается с проверкой и миграцией (`src/shared/pro/pinconfig/schema.ts`: файл без `schemaVersion` считается версией 0 и дополняется значениями по умолчанию; более новая версия — понятная ошибка), пишется в каноническом виде (выводы по порядку портов, ключи в фиксированном порядке).

```json
{
  "schemaVersion": 1,
  "chip": "stm32f103c8",
  "package": "LQFP48",
  "mode": "cmsis",
  "pins": { "PC13": { "role": "output", "initial": "high", "label": "LED" } },
  "peripherals": { "USART1": { "enabled": true, "baud": 115200, "signals": { "USART1_TX": "PA9", "USART1_RX": "PA10" } } },
  "clock": { "source": "pll", "pllSource": "hse", "hseHz": 8000000, "hseBypass": false, "pll": { "mul": 9 }, "ahbDiv": 1, "apb1Div": 2, "apb2Div": 1 }
}
```

- `pins`: роль GPIO (`input`, `output`, `analog`, `exti`), подтяжка, скорость, тип выхода, начальный уровень, метка, `confirmed` (подтверждено занятие защищённого вывода). Функции периферии лежат не здесь, а в `peripherals.<ИМЯ>.signals` (сигнал → вывод): так конфликт «вывод занят двумя ролями» хранится и виден явно. В таблице пинов роль вывода собирается из обоих мест.
- `peripherals`: включена ли периферия, назначение сигналов, параметры (пока только `baud` у USART; кадр всегда 8N1).
- `clock`: источник SYSCLK (`hsi`, `hse`, `pll`), источник PLL, частота и режим HSE, параметры PLL своего семейства, делители AHB/APB.
- `mode`: `cmsis` — код на регистрах, `hal` — только если в проекте есть заголовки HAL (`stm32…_hal.h`, ищутся в `drivers/` и `includes`).

### Проверки (`validate.ts`)

Вывода или сигнала нет в выбранном корпусе (по базе) — ошибка с подсказкой, где сигнал есть; одна роль на вывод — иначе «занят несколькими ролями» (включая выводы кварца HSE при тактировании от HSE); защищённые выводы (SWDIO/SWCLK, кварцы HSE/LSE, BOOT0) — ошибка, пока пользователь не подтвердит (диалог в инспекторе; JTAG PA15/PB3/PB4 у F1 разрешён, генератор отключает JTAG); F1: все выводы одной периферии должны быть из одного варианта ремапа AFIO; метки — допустимые и неповторяющиеся идентификаторы; частоты — по профилю семейства.

### Тактирование: что подтверждено и откуда

Границы и таблицы взяты из драйверов HAL ST и примеров STM32Cube (файлы прочитаны целиком, ссылки — в `CLOCK_SOURCES` в `src/shared/pro/pinconfig/clock.ts` и в разделе «Откуда взяты пределы» вкладки):

| Семейство | Что подтверждено | Подбор PLL и код |
|---|---|---|
| STM32F103 | HSE 4–16 МГц, SYSCLK ≤ 72, APB1 ≤ 36, APB2 ≤ 72 МГц, множитель PLL 2…16, wait states 0/1/2 (≤24/≤48/≤72 МГц) | есть, собрано для F103C8 |
| STM32F411 (и F407) | HSE 4–26 МГц, M 2…63, N 50…432, P 2/4/6/8, Q 2…15, вход VCO 1–2 МГц, выход 100–432 МГц, 100/100/50 МГц (F411) и 168/168/42/84 (F407), масштаб напряжения 1, 30 МГц на wait state при 3,3 В | есть, собрано для F411RE |
| STM32G4 | HSE 4–48 МГц, M 1…16, N 8…127, R 2/4/6/8, вход VCO 2,66–8 МГц, выход 64–344 МГц, все шины ≤ 170 МГц, таблица wait states режима boost, промежуточный делитель AHB /2 выше 80 МГц | есть, собрано для G474RE |
| F401, F446 | пределы шин известны | PLL «пока вручную» (для F401 масштаб напряжения не подтверждён, для F446 выше 168 МГц нужен Over-drive); HSI и HSE без PLL работают |
| F0, F3, L0, L1, L4, H7 | не собраны | «пока вручную»: код тактирования не создаётся, частоты не рассчитываются |

Известные числа из примеров ST проверяются юнит-тестами: F1 `HSI/2 × 16 = 64 МГц`, 2 wait states; F411RE `HSE 8 МГц, M=8 N=400 P=4 Q=7 → 100 МГц`, VCO 400 МГц, 3 wait states; G474RE `HSI 16 МГц, M=4 N=85 R=2 → 170 МГц`, VCO 340 МГц, 4 wait states; BRR USART — по таблице RM0008 (`72 МГц, 115200 бод → 0x271`, `36 МГц → 0x138`).

### Генерация кода

Кнопка «Сгенерировать код…» показывает план (какие файлы будут созданы или обновлены, сохранённые блоки USER CODE, предупреждения, diff для `main.c`) и пишет файлы только после подтверждения. Создаются `include/board.h`, `src/board.c` (`board_init()`, SysTick 1 мс, `board_millis()`, `board_delay_ms()`), `clock.{h,c}`, `gpio.{h,c}` (имена `LED_PORT`, `LED_PIN`, `LED_SET()`, `LED_RESET()`, `LED_TOGGLE()`, `BTN_READ()` из меток), `uart.{h,c}` (`usart2_write()`, `usart2_write_byte()`, `usart2_read_byte()`).

- Режим регистров CMSIS: имена регистров и битов из заголовков устройства, без HAL. Режим HAL (только при наличии HAL в проекте): `HAL_Init`, `HAL_RCC_OscConfig/ClockConfig`, `HAL_GPIO_Init`, `HAL_UART_Init`.
- Файлы помечены «СГЕНЕРИРОВАНО AVR IDE»; свой код — только в блоках `/* USER CODE BEGIN … */ … /* USER CODE END … */`. Повторная генерация идемпотентна, содержимое блоков переносится; блок, исчезнувший из шаблона, не теряется, а уходит в конец файла как `Orphan_<имя>`. Чужой файл с тем же именем (без отметки) перед перезаписью предупреждает в плане.
- `main.c`: по подтверждению добавляются `#include "board.h"` и `board_init();` первой строкой `main()` (вызов в комментарии не считается; повтор ничего не меняет). Открытый в редакторе `main.c` меняется там, закрытый — на диске.
- Поддержано: семейства F1, F4, G4; GPIO (вход, выход, аналог, альтернативные функции, подтяжка, скорость, начальный уровень, ремап AFIO и отключение JTAG у F1), USART1…3 (и USART6 у F4) со скоростью и расчётом BRR, тактирование, SysTick. Выводы остальной периферии (I2C, SPI, TIM, ADC, CAN …) настраиваются в режиме альтернативной функции, но её инициализация — «генерация не поддерживается, вручную» (подсказка в интерфейсе). EXTI: вывод настраивается как вход, прерывание не генерируется (предупреждение). Для остальных семейств генерация отключена с объяснением, файл конфигурации сохраняется.
- Направление сигналов F1 (у F1 нет номеров AF, режим вывода зависит от направления) известно генератору для USART, SPI (мастер), I2C, таймеров, CAN; прочее — предупреждение «настройте вручную».

Нужны `AVRIDE_E2E_GCC` (папка bin компилятора) и `AVRIDE_PRO_DIR` (кэш поддержки); HAL-случаи — ещё `AVRIDE_HAL_DIR` (папка с `f1`, `f4`, `g4`, в каждой `Inc` с `Inc/Legacy` и `Src` драйвера HAL ST). Без них тест пропускается.
- e2e: `scripts/e2e/scenarios/aa-pro-pins.mjs`; снимки обеих тем и ширин 1280/760 — `scripts/e2e/shots-pins.mjs` (два запуска: `--set a` и `--set b`).

### Что не проверено

- Запуск сгенерированной программы на плате (устройства нет): частоты, wait states и значения BRR проверены по документации и сборкой, не измерением.
- Инициализация I2C, SPI, таймеров, АЦП, USB, CAN; прерывания EXTI; PLL для F401 и F446 (выше 168 МГц), для F0, F3, L0, L1, L4, H7; режим HAL проверен сборкой, но не запуском.

## Умный редактор C/C++ (этап F)

В проекте STM32 C/C++ открываются как язык «avr-c» (своя подсветка без констант и функций Arduino; Arduino-провайдеры не затрагиваются). Подсказки строятся по **индексу символов проекта**: он понимает свои файлы (`sources`, `includes`) и все заголовки, которые они подключают через `#include` (CMSIS, HAL, библиотеки), в том числе заголовки из кэша пакета поддержки `userData/pro/support`, пока файлы CMSIS ещё не скопированы в проект.

### Индексатор (`src/shared/pro/cindex/`, `src/main/pro/symbols/`)

- Свой лёгкий разбор, без внешних зависимостей и нативной сборки: препроцессор (`#define`, `#if/#ifdef/#ifndef/#elif/#else` с вычислением константных выражений, `#include`) и объявления верхнего уровня (функции, прототипы, `static inline`, структуры, объединения, `enum`, `typedef`, указатели на функции, переменные, поля с массивами и битовыми полями, `extern "C"`, методы и поля классов C++). Doc-комментарии берутся из блока перед объявлением или из комментария в конце строки (`/*!< … */`).
- Условные ветки решаются по `defines` проекта, макросу устройства из базы чипов и макросам конфигурации. Макросы из других файлов учитываются по ходу включений (например, `__Vendor_SysTickConfig` из заголовка устройства открывает `SysTick_Config` в `core_cm3.h`): файлы с такой зависимостью перечитываются во втором проходе.
- Корни обхода — свои файлы проекта (вне `drivers/`, `Middlewares/`, `third_party/`, `vendor/`, `CMSIS/`); сторонние заголовки попадают в индекс только по `#include`, поэтому лишние заголовки устройств из папки `Include` не смешиваются. Ассемблер (`.s`): метки, `.equ`, `#define`.
- Из макросов вида `((GPIO_TypeDef *) GPIOA_BASE)` выводятся периферийные экземпляры, значения макросов и адреса вычисляются (`GPIOA_BASE → 0x40010800`), смещения регистров считаются по раскладке структуры (ARM, размеры `uint8_t…uint64_t`, массивы, объединения; структуры с битовыми полями и неизвестными типами смещения не получают).
- Работа в main, по файлам с уступкой цикла событий между ними (интерфейс не блокируется). Кэш разбора по пути, mtime, размеру и по значениям внешних макросов — `userData/pro/index/<хэш проекта>.json`. Несохранённый текст открытых файлов приходит из редактора (через 250 мс после правки) и разбирается заново только для этого файла.

### Что умеет редактор

| Действие | Как |
|---|---|
| Автодополнение | после `GPIOA->`, `RCC->`, `USART1->`, `g->` (локальная переменная или параметр) — поля структуры по порядку объявления с описанием и смещением; в выражении с регистром (`GPIOC->ODR |= GPIO_ODR_`) сначала маски битов именно этого регистра; обычные имена из индекса (свои символы выше), `#include "…"` — имена заголовков; ключевые слова, типы stdint |
| Сниппеты регистров | `gpio_out`, `gpio_in`, `gpio_set`, `gpio_reset`, `gpio_toggle`, `gpio_read` по семейству проекта (F1: CRL/CRH, F4 и G4: MODER/PUPDR, тактирование порта в нужном регистре RCC), а также `systick_1ms`, `systick_handler`, `nvic_enable`, `critical_section` |
| Hover | объявление, doc-комментарий (у определения функции — из прототипа), значение макроса (`0x10 (16)`), для периферии тип, базовый адрес и число регистров, для поля — смещение и адрес регистра (`GPIOC->ODR → 0x4001100C`), размер структуры |
| Подсказка параметров | функции и функциональные макросы из индекса |
| Переход | F12 и Ctrl+клик (слово подчёркивается при зажатом Ctrl): определение функции предпочитается прототипу, на самом определении — следующее объявление; `#include` ведёт к файлу; заголовок вне проекта открывается во вкладке «только чтение» |
| Ссылки | Shift+F12: список по границам слов в файлах проекта, без комментариев и строк (для `static` в `.c` — только в этом файле) |
| Символы | Ctrl+Shift+O — символы файла (встроенное окно Monaco, поля внутри структур), Ctrl+T — функции, макросы, типы, регистры проекта и подключённых заголовков |
| Переименование | F2: предпросмотр всех замен (старое/новое) и подтверждение; только символы своих файлов (функции, макросы, переменные, типы, константы, поля с уникальным именем); файлы записываются на диск, открытые вкладки обновляются; CMSIS/HAL и чужие имена не трогаются |
| Диагностика компилятора | строки и столбцы из gcc из «Проблем» — волнистая линия в редакторе (узкий диапазон растягивается до слова) |
| Форматирование | Shift+Alt+F через `clang-format` (`--style=file`, запасной LLVM), если он найден (`AVRIDE_PRO_CLANG_FORMAT`, папка IDE, STM32CubeIDE, LLVM, PATH); иначе пункт-подсказка «нужен clang-format». Своего формата нет |
| Подсветка | ассемблер GNU as для ARM (метки, директивы, регистры, мнемоники Thumb-2, `#include/#define`), скрипты ld, карта компоновки `.map`, `.svd` как XML |
| `avride.project.json` | подсказки ключей и значений (`core`, `optimization`, `programmer.kind` …), описания при наведении, диагностика: синтаксис JSON и `validateProject` с привязкой к строке поля |

### Что не поддержано

- Это не компилятор: нет полного разбора выражений и шаблонов C++, нет определения типов у сложных выражений (`(*p)->x`, результатов вызовов), нет подсветки неопределённых имён (ложные срабатывания хуже пользы). Локальные переменные — только для подсказок после `->`, не для перехода и ссылок.
- Переименование локальных переменных и параметров — через поиск и замену (Ctrl+H).
- Условия `#if` учитывают макросы проекта и определённые в заголовках, но не предопределённые макросы компилятора сверх небольшого набора (`__GNUC__`, `__arm__`, `__thumb__`); `__has_include` и подобное считаются ложными.
- Периферия из SVD в подсказках не используется: адреса и смещения берутся из заголовков CMSIS (SVD — только окно периферии отладчика).
- Сниппеты регистрового GPIO проверены компиляцией для F1, F4 и G4 (см. тесты); для F0, F3, L0, L1, L4, H7 GPIO-сниппеты не предлагаются (заголовки этих семейств в проверке не участвовали), общие сниппеты остаются.
- Индекс не следит за изменениями файлов вне IDE мгновенно: обновляется при возврате в окно, сохранении и смене конфигурации.
